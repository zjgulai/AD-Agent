# 广告监控与优化 Agent（一期：Meta）产品方案

## 核心问题

面向 Meta（Facebook / Instagram）投放团队的「广告监控&广告优化 Agent」一期要解决什么？它如何把人肉巡检 SOP 变成「自动巡检 → 异常诊断 → 飞书预警 → 安全边界内自动调整 → 全程留痕复核」的闭环？规则引擎与 LLM 如何分工才敢让系统碰真实账户？一期做什么、不做什么，评审前还有哪些决策与参数待拍板？

## 系统解答

### 1. 需求定位与业务价值

**一句话摘要（PRD 原文）**：建设面向 Meta 投放团队的自动化操作员——按既定 SOP 自动巡检全部投放对象，把异常变成带根因和带处置建议的预警，在安全边界内直接完成调整，并把每一次决策连同结果留痕，为二期学习投手经验积累数据。

- 需求级别 **A / P1**；业务逻辑复杂度 5/5、数据与系统集成复杂度 5/5，综合评级**高**；涉及工种 UI/UX、前端、后端、数开、测试；提出部门为广告部，对接数字化中心产品经理周文军；变更日志 V1.0（2026-11-11 初始评审稿）。
- 评审对象：增长投放负责人、广告优化师、数据与技术负责人；需产出 **5 项产品决策 + 待确认参数**（正文实际列 P1–P10 共 10 项，见 §9）。

**四个核心痛点 → 价值主张**：① 监控靠人肉轮询，异常发现滞后（发现即已损失数百美金）→ 系统盯盘，P0 级 30 分钟内触达；② 发现异常后没有归因过程、凭经验猜 → 五段式诊断卡带完整证据链；③ 调整后不追踪效果、经验无法沉淀 → 动作前快照 + 21 字段日志 + 4h/24h/72h 三段复核，「改完就忘」变「改完必验」；④ 投放知识锁在人脑里 → 一期沉淀的带证据决策数据是二期学习投手习惯的唯一前提。

**一期产品目标（G1–G5）**：

| 编号 | 目标 | 指标与口径 | 一期目标值 |
|------|------|-----------|------------|
| G1 | 在投对象不漏检 | 巡检覆盖率 = 已完成诊断对象数 ÷ 在投对象数 | 100% |
| G2 | 异常发现不滞后 | P0 告警触达时延 P95 | ≤ 30 分钟 |
| G3 | 每条告警都有依据 | 带完整五段式诊断卡的 P0、P1 告警占比 | 100% |
| G4 | 每次调整可追溯可回滚 | 动作日志完整率 = 填满必填字段的记录 ÷ 执行记录数 | 100% |
| G5 | 投手时间被释放 | 每周例行巡检 + 救急处理工时 | 基线待测，目标值待业务确认 `[待确认]` |

### 2. 总体设计：规则引擎 + LLM 双引擎

- **规则引擎负责「判断」**：65 个节点、196 条分支、25 项基准线是确定性规则，刻意不用 LLM——可解释、可追责、可被业务方直接修改，不受模型波动影响。
- **LLM 负责「理解、表达、沉淀、交互」**：预警叙事、根因排序与解释、周度审计聚合、二期习惯学习与自然语言问答。
- **定位一句话**：「规则引擎保证这个系统不会乱动，LLM 保证这个系统越用越聪明、越用越好懂。」
- **设计原则**：L3 决策层的规则内容完全来自策略树（S4），不由模型生成；LLM 只在规则候选集之内做排序、解释与聚合表达，不产生规则外的判断与动作。

**五层架构**：L5 呈现层（监控总览 / 预警中心 / 执行台 / 规则配置）→ L4 执行层（建议→人工确认→安全检查→执行→复核，观察/确认/自动三档）→ L3 决策层（诊断引擎 G0→G8 + 动作库 A-01~A-16 + LLM 能力 L1~L3）→ L2 规则层（25 项基准线 / P0-P2 优先级 / 冷却期 / 大促日历 / 动作白名单 / 权限档位 / 熔断器）→ L1 数据层（天级明细 / 小时级实时 / 配置快照 / 落地页漏斗 / 站点监测 / 订单对账 / 动作日志）。

### 3. 数据接入：双通道 + 配置快照

天级报告按天同步满足基准线比对，但 **Pacing（预算花费进度）、剩余预算、投放状态**等实时指标必须走小时级查询。PRD 引用的 Meta API 事实（均经公开资料核实，实现时以官方文档复核）：

| 事实 | 内容 | 来源 |
|------|------|------|
| 数据延迟 | insights 延迟约 15–30 分钟，小时级轮询可得近实时花费进度 | Ryze AI 指南（2026-05） |
| 小时粒度参数 | `breakdowns=hourly_stats_aggregated_by_advertiser_time_zone` + `time_increment=1` | 多篇 2026 实践文章一致 |
| 小时数据保留期 | 仅约 13 个月（2026-01-12 起官方变更），历史分析依赖天级层 | Meta 官方变更公告转述 |
| audience 时区维度 | `hourly_stats_aggregated_by_audience_time_zone` 需按账户开通（`POST /act_账户ID/insights/feature-settings`）；未开通返回 HTTP 200 但空数据（静默失败）`[待确认]`：PRD 调研表该行已加删除线，参考资料与 P8 仍保留该探测项 | AdBeacon（2026-08），PRD 有删改痕迹 |
| 剩余预算字段 | `budget_remaining` 为对象级字段，单位是账户币种最小单位（分），按 `currency_offset` 换算 | ads_management 官方 schema（Markifact 整理） |
| 限流机制 | 每个响应带 `X-Business-Use-Case-Usage` 头（call_count / total_cputime / total_time），ads_management 与 ads_insights 分开计量；用量达 80% 应降速，100% 返回错误码 17；配额按账户花费规模浮动 | Meta BUC 限流机制官方文档转述 |
| 大查询异步化 | 大范围查询走异步报告：提交得 `report_run_id`，轮询 `async_status` 取结果 | insights API 标准用法 |

**四条设计结论**：① 双通道——天级全量（T+1，基准线比对源）+ 小时级轮询（每 60 分钟，只跑 Pacing 类轻量快检）；② 实时层不做全量诊断，命中异常携带天级数据进完整诊断链，省 API 配额；③ M1 阶段必须对试点账户做小时级可用性探测；④ 所有同步任务统一读 BUC 响应头，80% 降速、100% 退避，大跨度回补走异步报告。

**三类同步任务**：批量同步每日 T+1 全量拉四层 insights 落 ODS→DWD（大跨度回补走异步报告，已完成）；实时轮询每 60 分钟拉小时级花费与 `budget_remaining`；配置快照每 4 小时拉四层对象的预算/出价/状态/受众/素材，用于动作前快照比对与 G8「近 12 小时人工变更」检查。

### 4. 诊断引擎：G0–G8 固定顺序 + 保护期闸门

诊断不并行、不跳级，严格按序执行；任一阶段命中「异常出口」即在该阶段收口（冻结 / 只监控 / 转人工），出口本身产出结构化事件供预警与日志：

| 阶段 | 职责 | 关键异常出口 |
|------|------|-------------|
| G0 数据可信度 | 判断数据/公式/事件是否可信 | 数据错误/追踪异常 → 冻结普通优化 |
| G1 资格与账户 | 账户、广告、页面投放资格 | 账户/页面异常 → P0 修复 |
| G2 追踪归因 | Pixel/CAPI/GA4 与归因窗口一致性 | EQ<4 或差异率>30% → 停止策略诊断 |
| G3 目标事件 | 投放目标、优化事件是否一致 | 目标事件错误 → 修正后重新学习 |
| G4 样本量 | 指标是否达可诊断门槛 | 样本不足 → 仅监控并预约复测 |
| G5 预算节奏 | 欠投/正常/超投与系列绩效 | 欠投/超投 → 走预算分支并结束本轮 |
| G6 目标专项 | 按曝光/引流/销售/重定向选指标链路 | 命中专项异常 → 执行对应动作 |
| G7 分层归因 | 定位国家/设备/版位/人群/素材/页面/商品根因 | 确认主因后**只执行一个主动作** |
| G8 动作安全 | 人工变更、大促、单变量、冷却期、回滚条件 | 不满足 → 只告警不自动执行 |
| 复核 | 动作是否有效，必要时回滚或升级 | 命中回滚条件 → 回滚并升级 |

65 节点分布：前置检查 5（P0-01~P0-05）+ 系列级 27（S1）+ 广告组级 16（S2）+ 创意级 15（S3）+ 后置 2（P4-01 安全检查、P4-02 复核回滚）= 65，196 条 IF 分支，规则内容逐条引自 S4 策略树（附录 A~D）。

**三个实现约定**：① 节点编号前缀 P0（如 P0-01 是「前置检查第一个节点」）与分支优先级 P0（止血级）语义不同，必须用 `node_id` 与 `priority` 两个字段分开承载；② 一次诊断只出一个主动作，数据结构层面强制（一轮诊断记录只有一个主动作字段）；③ 多分支同时触发时按「动作优先级排他矩阵」决策，非主动作降级为降级建议并记录。

**排他矩阵（止血优先、可逆性优先）**：① 暂停广告（A-05）> ② 缩减预算（A-04，缩 20%~50%）> ③ 刷新素材（A-09 换/补素材、A-10 前 3 秒重剪）> ④ 调整出价（A-08）。

**两道保护期前置闸门**（引擎级、所有诊断先过闸门；不是新增节点，节点数仍 65/196）：

| 保护期 | 触发 | 解除条件 | 期内行为 |
|--------|------|---------|---------|
| 新建对象冷启动保护期 | 新建 Campaign/Ad Set 上线 <24h，或预算消耗未达目标转化成本当量 | 上线 ≥24h **且** 消耗 ≥1 倍目标转化成本当量（具体参数 `[待确认]` P9） | 只监控记录，不下发止血/降预算/暂停；learning_status 只读展示 |
| 归因延迟缓冲期 | 全部在投对象：CAPI/Pixel 归因延迟 1~4h，归因窗口成熟度 <80% | 成熟度 ≥80% | 禁止判断 CPA/ROAS，仅诊断流量与成本侧指标；预警卡标注数据成熟度 |

保护期状态与剩余时间必须写回诊断日志并在工作台展示，让投手看得到「为什么没有动作」。

### 5. 六块交付物（F1–F7 + LLM 三能力）

| 编号 | 交付物 | 要点 |
|------|--------|------|
| F1 | 数据接入与刷新 | 天级全量 + 小时级实时双通道；延迟与成熟度可计算；数据不可信即冻结诊断（报表延迟 >6h 冻结；3~6h 照常但标注「置信度下降」；小时级 200 空数据静默失败须识别告警，不得误读为花费为 0） |
| F2 | 监控总览工作台 | 账户→系列→广告组→创意四层下钻；健康评分公式待评审确认 `[待确认]`（D4/P7）；学习期/样本不足/延迟对象不参与评分但须显式标注排除原因；异常优先+花费降序，P0 置顶不被分页折叠 |
| F3 | 异常检测与飞书预警 | 五段式卡片（异常/证据/根因/动作/影响预估）；分级触达；冷却期去重；LLM-1 文案；批量异常卡与一键批量处理；2 小时卡片生命周期与超时失效兜底 `[待确认]` P10 |
| F4 | 自动诊断引擎 | 65 节点/196 分支可配置规则；G0–G8 固定顺序；LLM-2 根因排序；保护期前置闸门；单主动作冲突排他矩阵 |
| F5 | 自动化调整执行台 | 三档执行权限；安全检查与熔断；动作前快照与自动回滚；执行台原型 P4 |
| F6 | 动作日志与复核 | 21 字段日志；4h/24h/72h 三段复核自动回填；周度决策审计（LLM-3）；人工与系统回填分别标记来源 |
| F7 | 规则与阈值配置 | 全局默认 + 维度覆盖（国家/目标/版位/设备/新客重定向/行业/季节）；变更留痕与回归对比；一期静态阈值 + 日常期/促销期模板一键切换与定时生效；动态基线排期二期 |
| LLM-1 | 预警解读文案 | 结构化诊断结果 → 投手可读预警叙事；失败降级为模板文案，卡片必达 |
| LLM-2 | 根因假设排序 | 在规则候选集内排序并解释（结合近 30 天同类事件动作日志检索），不产生规则外动作；目标首位命中率 ≥70%（以投手最终确认为标签，对比规则默认序基线） |
| LLM-3 | 周度决策审计报告 | 聚合动作日志产出达标率/回滚分析/误报集中指标/阈值调整建议；每个结论必须引用具体日志条目（诊断 ID/动作 ID），禁止无出处概括 |

**告警分级与触达**：紧急=P0 分支（共 14 条）→ 飞书卡片 + 电话/群升级，≤30 分钟；高危=P1（共 55 条）→ 飞书卡片，≤2 小时；中危/低危=P2（共 62 条）+ 趋势类 → 工作台聚合 + 每日摘要，当日处理。同对象同根因冷却期（默认 24h，可配）内合并降噪不重复推送；同监控周期同根因异常 ≥10 条聚合为「批量异常卡」（一键批量忽略 / 一键暂停整批组需二次确认）；「人工复核」档提案卡片 2 小时未处理自动失效、动作不执行 `[待确认]`（P10 是否提供「超时按默认规则执行」配置项）。

**三档执行权限**：

| 档位 | 行为 | 一期是否开放 |
|------|------|-------------|
| 观察模式 | 只巡检、只告警、只建议，绝不改投放设置（**默认档位**） | 是 |
| 确认模式 | 告警附完整动作建议，人工一键执行（**一期主推**） | 是 |
| 自动模式 | 条件满足即自动执行，无人干预；仅白名单低风险动作，**默认关闭、按账户逐一开启** | 是（默认关） |

一期白名单建议仅 A-02 预算+20%、A-04 预算缩减 20%~50%（P0 止血）、A-05 暂停劣质组/广告、A-07 增加排除名单、A-11 频次上限；明确排除 A-03 预算+50%、A-06 调整受众、A-08 调整出价、A-15 结构重构（影响面大/不可精确回滚/触发学习期重置）。

### 6. 防呆体系：安全边界、熔断、回滚、动作铁律

**G8 执行前安全检查（P4-01）**，四项任一不满足即不执行只告警：近 12 小时内该对象有人工变更；处于大促窗口（大促日历判定）；冷却期不满足；回滚条件缺失。执行器调 Meta API 前还有**二次安全检查**：单次调整幅度超限截断到上限并标记（如预算调整单次不超 30%）；当日该账户动作数超熔断阈值则停止执行转人工；动作前快照缺失禁止执行。

**四维熔断（建议一期默认阈值）**：

| 熔断维度 | 阈值 | 触发后动作 |
|---------|------|-----------|
| 动作数量（防批量误杀） | 单账户单周期 ≤5 个关停/降预算动作；单账户单日自动调整 ≤20% 在投广告组 | 拦截超限动作，全部降级为人工审批卡片并告警 |
| 资金消耗（防预算跑飞） | 1 小时消耗 ≥40% 日预算；单日总消耗 >120% 预算 | **最高优先级强制执行**：直接暂停对应广告组 + 加急告警（应对 Meta Overspend Bug） |
| 预算设置 | 单次调整幅度 >100% | 拦截，降级人工审批卡片并告警 |
| 技术接口（防封号/雪崩） | Meta API 连续 5 次报错或 10 分钟内错误率 ≥30%；LLM 连续 3 次超时（>15s） | API 熔断：暂停自动下发 15 分钟退避重试；LLM 熔断：跳过文案解读直接发纯规则告警 |

**动作铁律（硬约束）**：① 一次只动一个主变量；② 学习期不判效；③ 动作后必须复核（4h/24h/72h，缺复核视为未闭环）；④ 冷却期 24–72h（默认 24h，可按动作类型配）；⑤ 归因窗口成熟度 <80% 禁止判断 CPA/ROAS；⑥ 多分支同时触发按排他矩阵只保留一个主动作。

**执行后复核与回滚（P4-02）**：执行即写 21 字段日志并创建三段复核任务。判定：CPA 上升 ≥20% 或 ROAS 下降 ≥20% 或数据延迟 >6h → 自动回滚最近动作 + 升级 P0 告警；CPA +10%~20% 或 ROAS -10%~20% 或延迟 4~6h → 待观察、禁止追加动作；其余 → 达标闭环。**建议熔断** `[待确认]`：同一账户 7 天内触发 ≥2 次自动回滚，自动模式自动降级为观察模式并通知负责人，直至人工重新开启。

### 7. 数据需求：十个数据域 + 小时级实时层

策略树每个节点标注所需数据源，汇总为 10 个数据域（日级为主）：广告系列/广告组/创意三级投放数据（Meta 广告 API，四层 × 天）、落地页漏斗（站内埋点）、站点监测（HTTP 状态/404/LCP）、后台订单对账（业务订单系统，盈亏平衡 ROAS 来源）、事件日志（EQ 事件质量评分）、账户状态报表、动作日志（系统自建）、大促日历与阈值配置（业务方维护）。小时级实时层仅 3 项（小时级花费/剩余预算/投放状态，60 分钟轮询），只保留近 14 天明细。

**数据侧三条硬要求**：① 归因窗口成熟度必须可计算（否则「<80% 禁判 CPA/ROAS」铁律无法执行）；② 分层能力到位——行业教训是主 ROAS 正常会掩盖单点异常（某目标 CPL +50% 被大盘盖住），三级数据须能按国家/版位/设备/人群下钻；③ 对账表是盈亏平衡 ROAS 唯一来源，缺失时 ROAS 类节点判「数据不足」，不得用行业默认值替代。

### 8. LLM 智能体：分层能力与安全护栏

能力分五层：L1 预警解读、L2 根因假设排序、L3 决策审计报告为**一期交付**；L4 投手习惯学习、L5 自然语言交互为**二期**。

**一期三能力约束**：LLM-1 用固定模板槽位 + 诊断 JSON 生成叙事，不引入诊断外事实、数字原样来自输入、长度控制在卡片可读范围；LLM-2 只做候选集内排序/解释/置信度，**排序不改变规则优先级与动作选择**；LLM-3 每结论须引用日志条目。

**安全护栏**：候选集约束（不产生规则外动作/阈值）、事实约束（数字与对象名原样来自输入，字段级校验不过降级模板文案）、优先级隔离（不覆盖 P0/P1/P2、不跳过 G8、不缩短冷却期）、三级失败降级（LLM 超时→规则默认序+模板文案；连续失败→关闭 LLM 增强并公告；规则诊断链任何情况下独立可运行）、全量留痕（输入摘要/输出/耗时/是否降级入审计日志）。

**工程与成本**：LLM 只在预警生成、根因排序、周度报告三个低频环节调用，不进实时巡检循环；上下文按「诊断 JSON + 动作日志按对象与时间窗检索」注入，不全量塞入；单次调用 ≤5 秒（预警文案对延迟敏感）；模型用公司内部可用服务，选型评审后定 `[待确认]` D5。

### 10. 一期范围边界与二期展望

- **一期范围**：仅 Meta 广告账户；规则引擎 + LLM（L1–L3）+ 三档权限 + 白名单自动执行 + 全量留痕；静态阈值配日常/促销模板切换；合规域（政策更新、违规词检测）一期仅提示不处置；素材轮换动作标注「本期不做」；平台无关封装留口（Google/TikTok 接入不改诊断引擎）。
- **二期方向**：L4 投手习惯学习（从「情境—判断—结果」三元组挖掘偏好，生成个性化策略画像）+ LLM-4；L5 自然语言交互 + LLM-5；分级放权（对象级→账户级→跨账户，准入看上一级运行结果）；滚动动态基线（对象×时段的 ROAS/CPA/频次异常判定线，替代或补充静态阈值，保留回退开关）。
- **二期四条红线**：学习结果不覆盖安全铁律；样本量门槛不被绕过；可解释性不牺牲（每步须说清「谁的习惯+哪条证据」）；学习与放权分离（放权须人显式授权、随时可撤）。

### 11. 非功能需求、验收与排期

- **非功能**：单账户完整巡检 ≤5 分钟；告警检测 P95 ≤30 分钟；小时级轮询单账户 ≤1 分钟；工作台按角色分权、机器人权限不超被授权账户；所有配置变更/告警流转/动作执行回滚/LLM 调用写入不可删除审计日志；白名单/冷却期/安全检查/回滚四重约束不可绕过（绕过需二次审批）；Meta 接口不可用降级只读监控并标注「本轮诊断不完整」；LLM 不可用降级规则默认序。
- **里程碑（相对周次，假设 2 后端/数据 + 1 前端 + 1 产品 + 投放 0.5 人）**：M0 规则确认（第 1 周）→ M1 数据就绪（2–3 周，10 数据域 + 限流治理）→ M2 巡检与预警（4–5 周，观察+确认模式，LLM-1/2）→ M3 执行与闭环（6–8 周，F5/F6 + 白名单自动模式默认关 + LLM-3）→ M4 校准与验收（9–10 周，阈值校准 + 连续 4 周试运行）→ M5 二期立项（第 11 周）。
- **验收关键项**：巡检覆盖率 100%；随机抽 20 节点与策略树一致率 100%；P0 送达 P95 ≤30min 且连续 4 周无漏报；P0/P1 告警 100% 带五段式卡；自动执行安全检查通过率 100%、构造 10 次违规场景拦截率 100%；回滚成功率 100%；日志必填字段缺失率 0、三段复核按时回填率 ≥90%；任一结论可展开判定链路；**灰度路径：1 个 Meta 账户观察模式 2 周 → 确认模式 → 1 个账户自动模式**；LLM 文案可读率 ≥90%、根因首位命中率 ≥70%、断开 LLM 链路不中断。
- **主要风险**：归因口径不准致误判（高，前置检查强制拦截）；阈值默认值不适配（高，M4 校准 + 回归对比）；自动执行事故（高，四重约束 + 回滚 + 7 天 2 次回滚降级）；告警噪音（中，分级触达 + 冷却期 + 周审计调阈值）；大盘掩盖单点异常（中，强制分层监控）；日志不全二期落空（中，必填字段系统层强制）；BUC 配额受限（中，80% 降速/100% 退避/异步报告）；学习期误判（中，样本量门槛 + 成熟度铁律）；LLM 幻觉改写数字/对象名（中，字段级校验 + 候选集约束）。

## 高频问答索引

- **Q：这个 Agent 一期到底做什么？**
  A：面向 Meta 投放团队的自动化操作员——按既定 SOP（S4 策略树：65 节点/196 分支）自动巡检账户→系列→广告组→创意全量对象，异常变成带根因和处置建议的飞书预警，在安全边界内直接完成调整（白名单低风险动作），并把每次决策连同 4h/24h/72h 复核结果留痕，为二期学习投手经验积累数据。
- **Q：它不做什么？一期边界在哪？**
  A：仅覆盖 Meta（Facebook/Instagram）账户；不做动态基线（一期静态阈值+日常/促销模板切换，滚动均值排期二期）；合规域（政策更新、违规词）一期仅提示不处置；素材轮换标注本期不做；LLM 只做 L1–L3（预警文案/根因排序/周审计），L4 习惯学习与 L5 自然语言交互是二期；跨平台（Google/TikTok）仅做数据层/诊断层无关封装留口。
- **Q：它会不会乱动广告账户？防呆机制有哪些？**
  A：五层防线：① 规则引擎判断不靠 LLM，且有两道保护期闸门（冷启动 <24h、归因成熟度 <80% 只监控不判效不动作）；② G8 执行前安全检查四项（近 12h 人工变更/大促窗口/冷却期/回滚条件缺失）+ 执行器二次检查（幅度截断、熔断转人工、快照缺失禁执行）；③ 四维熔断（动作数量/资金消耗/预算设置/技术接口）；④ 动作前快照 + 21 字段日志 + 自动回滚；⑤ 三档权限默认观察模式，自动模式默认关闭、白名单仅 5 个低风险动作且按账户开启。
- **Q：LLM 在系统里干什么？会不会幻觉出错误建议？**
  A：LLM 只做四件规则引擎做不了的事：预警叙事（LLM-1）、候选根因集内排序解释（LLM-2）、周度审计聚合（LLM-3）、二期习惯学习。护栏：只在候选集内工作不产生规则外动作；数字与对象名必须原样来自输入并做字段级校验，不过则降级模板文案；不覆盖规则优先级、不跳过 G8；三级失败降级，规则诊断链任何情况下独立可运行。
- **Q：数据从哪来？实时性怎么保证？**
  A：Meta Marketing API 双通道——天级全量 T+1（诊断基准线比对）+ 小时级每 60 分钟轮询（只跑 Pacing 类快检：花费进度/剩余预算/投放状态）；另有每 4 小时配置快照（供回滚与人工变更检查）；辅以落地页漏斗、站点监测、后台订单对账、事件日志（EQ）、账户状态共 10 个数据域。报表延迟 >6h 冻结诊断，3–6h 标注置信度下降；BUC 限流 80% 降速、100% 退避，大查询走异步报告。
- **Q：诊断是怎么走的？为什么敢说结论有依据？**
  A：G0→G8 九阶段固定顺序不并行不跳级：数据可信度→资格账户→追踪归因→目标事件→样本量→预算节奏→目标专项→分层归因→动作安全，外加动作后复核。任一阶段异常出口即收口不进入下一阶段；每个节点判定（命中分支/当前值/阈值/依据来源）全部落库，任一结论可在界面展开完整判定链路。同一轮只产出一个主动作，多分支命中按排他矩阵（暂停>缩预算>换素材>调出价）强制只留一个。
- **Q：告警怎么分级？怎么防止卡片轰炸投手？**
  A：P0（14 条分支）紧急级飞书卡片+电话/群升级 ≤30 分钟；P1（55 条）高危飞书卡片 ≤2 小时；P2（62 条）+趋势类进工作台聚合+每日摘要。五段式卡片（异常/证据/根因/动作/影响预估）。去重靠冷却期（默认 24h 可配）；同周期同根因 ≥10 条聚合为一张批量异常卡（可一键批量忽略/一键暂停整批组）；提案卡片 2 小时超时自动失效不执行 `[待确认]` P10。
- **Q：新上线的广告、学习期对象会不会被误杀？**
  A：不会——两道引擎级前置闸门：新建对象冷启动保护期（上线 <24h 或消耗未达 1 倍目标转化成本当量，只监控不动作，参数待 P9 确认）与归因延迟缓冲期（成熟度 <80% 禁止判断 CPA/ROAS，只诊断流量成本侧）；另有铁律「学习期不判效」「样本不足仅监控预约复测」。保护期状态写回日志并在工作台展示。
- **Q：执行了动作之后怎么验证有效？失败怎么办？**
  A：执行即写 21 字段动作日志并创建 4h/24h/72h 三个复核任务自动回填。复核判定：CPA +≥20% 或 ROAS -≥20% 或延迟 >6h → 自动回滚到动作前快照 + 升级 P0 告警；+10%~20% 区间 → 待观察禁止追加；达标 → 闭环沉淀为正样本。回滚本身也是动作同样留痕。建议熔断：7 天内 ≥2 次回滚自动降级观察模式 `[待确认]`。
- **Q：一期效果怎么评估？**
  A：五个产品目标 G1–G5（巡检覆盖率 100%、P0 送达 P95 ≤30min、P0/P1 告警 100% 带五段式卡、日志完整率 100%、投手工时释放[基线待测]）+ 11 条可测验收标准（含规则一致性抽查 100%、构造违规场景拦截率 100%、回滚成功率 100%、日志缺失率 0、复核回填率 ≥90%、LLM 文案可读率 ≥90%、根因首位命中率 ≥70%）。上线走灰度：1 账户观察 2 周 → 确认模式 → 1 账户自动模式。
- **Q：排期和试点怎么安排？**
  A：M0–M5 共约 11 周（相对周次）：M0 规则确认与决策拍板 → M1 十个数据域接入+限流治理 → M2 巡检预警（观察+确认模式）→ M3 执行闭环（白名单自动模式默认关+周审计）→ M4 阈值校准+4 周试运行验收 → M5 二期立项评估。试点建议 1 个 Meta 账户起步 `[待确认]` P5。
- **Q：规则阈值从哪来？业务方能改吗？**
  A：一期直接采用 S4 策略树的 25 项指标基准线作为默认值（附录 B 全表），动作库 16 项（附录 C）、日志模板 21 字段（附录 D）逐条对照。F7 支持「全局默认+维度覆盖」两级配置，阈值修改必须留痕（谁/何时/从什么改成什么）、历史结论不回溯改写、修改前后各跑一次回归诊断输出差异；日常期/促销期两套模板一键切换+定时生效。动态基线（滚动 7 天均值）排期二期。
